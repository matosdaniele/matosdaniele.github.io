Identificar um login esquecido pelo usuário

O DBA localiza o login perdido consultando privilégios e objetos de servidor, logs de falha ou entrada, DMVs de conexão e — se estiver configurada — a auditoria. As informações essenciais do usuário aceleram a busca.

Exemplos validados no Microsoft SQL Server 2025 (RTM) 17.0.1000.7, Enterprise Developer Edition, com a base AdventureWorks2025.

O problema

O administrador criou um login para alguém usar o banco AdventureWorks2025. A pessoa conectou na primeira vez. Cinco dias depois precisa entrar de novo e não lembra qual era o usuário. Com vários logins na mesma instância, a memória não resolve: o caminho é cruzar o que o SQL Server já guarda com o que a pessoa ainda consegue informar.

Login não é o mesmo que usuário

No SQL Server há dois níveis. Misturar os dois nomes atrapalha a busca.

Login
Conta na instância (servidor). É o que a pessoa digita para autenticar: SQL login ou conta do Windows.
Usuário
Conta dentro de um banco. Liga o login ao AdventureWorks2025 e às permissões daquele banco.

O vínculo entre os dois é o SID. A consulta útil junta o login do servidor ao usuário do banco pelo mesmo identificador — e, quando o nome falha, o SID ainda pode revelar a conta Windows mapeada.

O que pedir ao usuário antes de consultar

Quanto mais contexto, menos lista para vasculhar. Peça o que der:

  • Horário aproximado da tentativa ou do uso.
  • Host / hostname ou IP do cliente.
  • Aplicação usada (SSMS, app web, serviço).
  • Se foi autenticação SQL ou Windows (ex.: tentou teste ou DOMÍNIO\usuario).
  • Mensagens de erro completas (incluindo o state do erro 18456).
  • Se for serviço: se usa conta de serviço (NT SERVICE\... ou conta de domínio).

Passo 1 — quem tem acesso ao AdventureWorks2025

Comece pelo banco. A lista deixa de ser “todos os logins da instância” e vira “quem de fato tem usuário neste banco”.

T-SQL 

        
USE AdventureWorks2025;
GO

SELECT
  dp.name        AS usuario_no_banco,
  sp.name        AS login_no_servidor,
  dp.type_desc   AS tipo_usuario,
  sp.type_desc   AS tipo_login,
  dp.create_date AS usuario_criado_em,
  sp.create_date AS login_criado_em
FROM sys.database_principals AS dp
LEFT JOIN sys.server_principals AS sp
  ON dp.sid = sp.sid
WHERE dp.type IN ('S', 'U', 'G')
  AND dp.name NOT IN ('dbo', 'guest', 'INFORMATION_SCHEMA', 'sys')
ORDER BY sp.create_date DESC;

      

    

    
S é SQL user, U é usuário Windows e G é grupo Windows. login_no_servidor vazio costuma indicar usuário órfão: existe no banco, mas o login correspondente não está mais na instância.


    
Passo 2 — procurar e listar logins no servidor

    
As consultas abaixo são de leitura. Se a pessoa lembra de um pedaço do nome:

    

      

        T-SQL
        
      

      

        

        
SELECT name, type_desc, create_date
FROM sys.server_principals
WHERE name LIKE '%parte_do_nome%';

      

    

    
Para ver logins SQL e Windows com propriedades úteis (banco padrão, desabilitado):

    

      

        T-SQL
        
      

      

        

        
SELECT
  p.name,
  p.type_desc,
  l.default_database_name,
  l.is_disabled
FROM sys.server_principals AS p
LEFT JOIN sys.sql_logins AS l
  ON p.principal_id = l.principal_id
WHERE p.type IN ('S', 'U');  -- S = SQL login, U = Windows login

      

    

    
Se o administrador lembra a janela em que criou a conta (por exemplo, perto do primeiro acesso):

    

      

        T-SQL
        
      

      

        

        
SELECT name, type_desc, create_date
FROM sys.server_principals
WHERE type IN ('S', 'U')
  AND create_date >= DATEADD(day, -10, SYSDATETIME())
ORDER BY create_date DESC;

      

    

    
Cruze com o passo 1: só interessam logins que também aparecem como usuário no AdventureWorks2025.


    
Passo 3 — mapear SID → nome Windows

    
Útil quando sobra só o SID, ou quando o nome no catálogo não bate com o que a pessoa digita no cliente:

    

      

        T-SQL
        
      

      

        

        
SELECT
  name,
  sid,
  SUSER_SNAME(sid) AS mapped_name
FROM sys.server_principals
WHERE sid IS NOT NULL;

      

    


    
Passo 4 — conexões ativas e clientes recentes

    
O SQL Server não guarda, por padrão, uma coluna “último login” em sys.server_principals. As DMVs abaixo mostram quem está conectado agora (ou ainda presente nesta memória) — host, IP, aplicação e horário do logon da sessão:

    

      

        T-SQL
        
      

      

        

        
SELECT
  s.session_id,
  s.login_name,
  s.host_name,
  c.client_net_address,
  s.program_name,
  s.login_time
FROM sys.dm_exec_sessions AS s
JOIN sys.dm_exec_connections AS c
  ON s.session_id = c.session_id
WHERE s.login_name LIKE '%parte_do_nome%';

      

    

    
Se a pessoa puder tentar conectar de novo enquanto o DBA observa, host, IP e program_name (SSMS, app, serviço) costumam fechar o caso rápido.


    
Passo 5 — error log: falhas e entradas

    
Com auditoria de logon habilitada (ou pelo menos falhas registradas), o error log guarda tentativas. Exige permissão adequada — em geral perfil de sysadmin ou equivalente para xp_readerrorlog.

    

      

        T-SQL
        
      

      

        

        
-- Falhas de login no arquivo atual do error log
EXEC master.sys.xp_readerrorlog
  0,
  1,
  N'Login failed for user';

-- Filtrar por trecho do nome
EXEC master.sys.xp_readerrorlog
  0,
  1,
  N'Login failed for user',
  N'parte_do_nome';

      

    

    
Se a auditoria de logon bem-sucedido estiver ligada, busque também o primeiro acesso (cerca de cinco dias atrás no cenário deste texto):

    

      

        T-SQL
        
      

      

        

        
EXEC master.sys.xp_readerrorlog
  0,
  1,
  N'Login succeeded';

      

    

    
Sem acesso a xp_readerrorlog, use o Object Explorer: Management → SQL Server Logs. Compare horário, nome tentado e — se a mensagem trouxer — o state do 18456 com o que o usuário enviou.


    
Passo 6 — SQL Audit (se configurada)

    
Com auditoria de servidor ou de banco ativa, liste os arquivos e leia com sys.fn_get_audit_file, ou consulte as especificações nas catalog views (sys.server_audits, sys.server_audit_specifications, etc.). O detalhe depende do que a trilha foi configurada para gravar — logon bem-sucedido, falha, ou ambos.


    
Como confirmar antes de resetar senha

    
Achei um candidato. Antes de alterar senha ou desbloquear conta, confirme o mapeamento no banco e, se possível, com a própria pessoa.

    

      

        T-SQL
        
      

      

        

        
USE AdventureWorks2025;
GO

SELECT
  sp.name AS login_no_servidor,
  dp.name AS usuario_no_banco,
  dp.authentication_type_desc
FROM sys.server_principals AS sp
INNER JOIN sys.database_principals AS dp
  ON sp.sid = dp.sid
WHERE sp.name = N'login_candidato';

      

    

    
Se o nome do login e o do usuário forem diferentes (comum com dominio\pessoa), mostre os dois: o que a pessoa digita na conexão é o login.


    
O que mais checar

    
    
      
  • Active Directory (contas de domínio): confirmar UPN ou domínio\usuário.
    • 
      
  • Logs do Windows Application / Security para autenticações Windows.
    • 
      
  • Instância remota: confirmar servidor e nome da instância corretos.
    • 
      
  • Conta de serviço: NT SERVICE\... ou conta de domínio usada pelo aplicativo.
    • 
    


    
Permissões

    
    
      
  • Leitura de sys.server_principals e DMVs de sessão/conexão: em geral disponível a quem administra ou tem VIEW SERVER STATE / VIEW DATABASE STATE conforme o objeto.
    • 
      
  • Error log / xp_readerrorlog e SQL Audit: normalmente sysadmin (ou permissão equivalente na auditoria).
    • 
    


    
O que evita o susto da próxima vez

    
    
      
  • Padrão de nome: login alinhado a e-mail ou matrícula.
    • 
      
  • Registro mínimo: quem pediu, para qual banco, data da criação.
    • 
      
  • Auditoria de logon (sucesso e/ou falha) quando a política permitir.
    • 
      
  • Orientar o usuário a guardar o login no gerenciador de senhas da empresa.
    • 
    


    
Em uma frase

    
Com muitos logins na instância, o DBA identifica a conta pedindo horário, host, aplicação e tipo de autenticação; cruza sys.server_principals com os usuários do AdventureWorks2025 pelo SID; usa DMVs se a sessão ainda existir; e, com permissão, lê error log ou SQL Audit — não a memória de quem criou o login.

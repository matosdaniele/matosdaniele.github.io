Guardar o significado do objeto no banco

Nome de tabela e tipo de coluna dizem a forma. A descrição diz o significado. Guardar esse significado no próprio banco — via extended properties / MS_Description — evita que a documentação se perca fora do modelo.

Exemplos validados no Microsoft SQL Server 2025 (RTM) 17.0.1000.7, Enterprise Developer Edition, com a base AdventureWorks2025.

Por que documentar dentro do banco

Planilha, wiki e comentário em ticket envelhecem longe do objeto. A MS_Description fica colada à tabela, à coluna ou à procedure — e viaja com o backup, o restore e o script de deploy.

  • Documentação co‑localizada — fica junto ao objeto e não se perde fora do banco.
  • Manutenção e governança — facilita impacto, linhagem e análise de mudanças (quem, por quê, formato).
  • Onboarding e suporte — novos desenvolvedores e DBAs entendem o modelo sem caçar docs externas.
  • Ferramentas e automação — SSMS, dicionários, scripts e ETL/metadata leem automaticamente.
  • Consistência e rastreabilidade — reduz divergência entre código e documentação; permite gerar dicionários atuais.
  • Compliance e controle — útil na auditoria e como evidência de regra de negócio ou sensibilidade do dado.

Boas práticas rápidas

  • Padronize chaves e conteúdo (ex.: MS_Description com texto estruturado: finalidade, valores permitidos, unidades).
  • Salve os scripts de criação e alteração de extended properties no controle de versão.
  • Use texto objetivo e exemplos; evite duplicar o que o nome ou a constraint já deixam óbvio.
  • Garanta permissão adequada (VIEW DEFINITION para leitura; permissão de alteração para gravar).
  • Atualize a descrição sempre que o objeto mudar — inclua data e autor quando for relevante.

Para criar use sp_addextendedproperty. Se a propriedade já existir, use sp_updateextendedproperty com os mesmos níveis (SCHEMA / TABLE / COLUMN).

Adicionar descrição de tabela

No AdventureWorks2025 a loja está em Sales.Store. O padrão abaixo grava (ou atualiza, se você trocar o procedure) a descrição da tabela:

T-SQL 

        
EXEC sp_addextendedproperty
  @name = N'MS_Description',
  @value = N'Tabela de lojas: contém informações de endereço e gerente.',
  @level0type = N'SCHEMA', @level0name = N'Sales',
  @level1type = N'TABLE',  @level1name = N'Store';
GO

EXEC sp_addextendedproperty
  @name = N'MS_Description',
  @value = N'Código identificador da loja (PK, INT).',
  @level0type = N'SCHEMA', @level0name = N'Sales',
  @level1type = N'TABLE',  @level1name = N'Store',
  @level2type = N'COLUMN', @level2name = N'BusinessEntityID';
GO

      

    


    
Consultar o dicionário da tabela

    
A consulta abaixo monta um recorte de dicionário: colunas, tipo, nulo, identidade, default, PK, FK e as descrições (MS_Description) da coluna e da tabela.

    

      

        T-SQL
        
      

      

        

        
DECLARE @schema sysname = 'Sales';
DECLARE @table  sysname = 'Store';
DECLARE @objid  int     = OBJECT_ID(QUOTENAME(@schema) + '.' + QUOTENAME(@table));

IF @objid IS NULL
BEGIN
    PRINT 'Tabela não encontrada.';
END
ELSE
BEGIN
    SELECT
      s.name AS schema_name,
      t.name AS table_name,
      c.name AS column_name,
      tp.name AS data_type,
      c.max_length,
      c.precision,
      c.scale,
      CASE WHEN c.is_nullable = 1 THEN 'YES' ELSE 'NO' END AS is_nullable,
      CASE WHEN ic.object_id IS NOT NULL THEN 1 ELSE 0 END AS is_identity,
      df.definition AS default_definition,
      CASE WHEN pk.index_id IS NOT NULL THEN 1 ELSE 0 END AS is_primary_key,
      fk.ref_schema + '.' + fk.ref_table AS referenced_object,
      col_ep.value AS column_description,
      tbl_ep.value AS table_description
    FROM sys.schemas AS s
    JOIN sys.tables AS t
      ON t.schema_id = s.schema_id AND t.object_id = @objid
    JOIN sys.columns AS c
      ON c.object_id = t.object_id
    LEFT JOIN sys.types AS tp
      ON tp.user_type_id = c.user_type_id
    LEFT JOIN sys.identity_columns AS ic
      ON ic.object_id = c.object_id AND ic.column_id = c.column_id
    LEFT JOIN sys.default_constraints AS df
      ON df.parent_object_id = c.object_id
     AND df.parent_column_id = c.column_id
    LEFT JOIN (
      SELECT i.object_id, i.index_id
      FROM sys.indexes AS i
      WHERE i.is_primary_key = 1
    ) AS pk
      ON pk.object_id = t.object_id
    OUTER APPLY (
      SELECT TOP (1)
        rs.name AS ref_schema,
        rt.name AS ref_table
      FROM sys.foreign_key_columns AS fkc
      JOIN sys.objects AS rf
        ON rf.object_id = fkc.referenced_object_id AND rf.type = 'U'
      JOIN sys.tables AS rt
        ON rt.object_id = rf.object_id
      JOIN sys.schemas AS rs
        ON rs.schema_id = rt.schema_id
      WHERE fkc.parent_object_id = c.object_id
        AND fkc.parent_column_id = c.column_id
    ) AS fk
    LEFT JOIN sys.extended_properties AS col_ep
      ON col_ep.major_id = c.object_id
     AND col_ep.minor_id = c.column_id
     AND col_ep.name = 'MS_Description'
    LEFT JOIN sys.extended_properties AS tbl_ep
      ON tbl_ep.major_id = t.object_id
     AND tbl_ep.minor_id = 0
     AND tbl_ep.name = 'MS_Description'
    ORDER BY c.column_id;
END;

O export completo da consulta (incluindo max_length, precision, scale, identidade e descrição da tabela) está no repositório público documentos-trilhas / bancodedados / Guardar o significado do objeto no banco.

    
A coluna PK aparece como 1 em todas as linhas porque a consulta marca a existência de chave primária na tabela, não a coluna participante — útil como alerta de modelo; para listar só as colunas da PK, o join com sys.index_columns seria o próximo ajuste.


    
Em uma frase

    
Guardar o significado com MS_Description deixa a documentação onde o objeto vive: o DBA e as ferramentas leem o dicionário direto do catálogo, e o modelo deixa de depender de um arquivo que ninguém atualiza.

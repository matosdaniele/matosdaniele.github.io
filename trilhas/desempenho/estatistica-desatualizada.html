Estatística desatualizada, plano errado

O SQL Server escolhe o caminho de uma consulta a partir de quantas linhas ele acha que vai encontrar. Quem diz isso a ele são as estatísticas. Quando elas envelhecem, a estimativa erra, o plano erra junto, e a consulta que era rápida fica lenta sem ninguém ter mudado uma linha de código.

Exemplos para o Microsoft SQL Server 2025 (RTM) 17.0.1000.7, com a base AdventureWorks2025. A demonstração cria e apaga uma tabela própria; rode num ambiente de estudo, nunca em produção.

O problema

Um relatório que levava segundos passa a levar minutos. O código é o mesmo, o servidor é o mesmo, os índices são os mesmos. O que mudou foi o volume: entrou uma carga grande numa tabela, ou um valor que era raro ficou comum. O banco continua planejando a consulta com a fotografia antiga dos dados.

O que é uma estatística

Estatística é um resumo da distribuição dos valores de uma ou mais colunas. O otimizador de consultas lê esse resumo para estimar quantas linhas cada etapa da consulta vai devolver — e, com essa estimativa, decide se busca pelo índice ou lê a tabela inteira, que tipo de junção usa e quanta memória reserva.

Histograma
Até 200 faixas (steps) da primeira coluna da estatística, com quantas linhas existem em cada valor de corte e entre um corte e outro. O menor e o maior valor da coluna sempre viram faixas.
Densidade
Quanto os valores se repetem, em média. Entra na conta quando o valor procurado não é conhecido na hora de compilar.
Contador de modificações
Quantas alterações a coluna sofreu desde a última atualização da estatística. É o que indica que a fotografia envelheceu.

Todo índice ganha uma estatística com o mesmo nome. O SQL Server também cria estatísticas sozinho, em colunas usadas em filtros e junções, quando a opção AUTO_CREATE_STATISTICS está ligada — essas aparecem com nomes como _WA_Sys_....

Passo 1 — ver as estatísticas de uma tabela

A consulta abaixo lista as estatísticas de Sales.SalesOrderDetail, com a data da última atualização, quantas linhas havia, quantas foram lidas para montar o resumo e quantas modificações aconteceram depois:

T-SQL 

        
USE AdventureWorks2025;
GO

SELECT
  s.name                  AS estatistica,
  s.auto_created          AS criada_pelo_banco,
  sp.last_updated         AS atualizada_em,
  sp.rows                 AS linhas,
  sp.rows_sampled         AS linhas_lidas,
  sp.modification_counter AS modificacoes
FROM sys.stats AS s
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS sp
WHERE s.object_id = OBJECT_ID(N'Sales.SalesOrderDetail')
ORDER BY sp.modification_counter DESC;

      

    

    
Quando linhas_lidas é menor que linhas, a estatística foi montada por amostragem. Em tabelas grandes isso é normal, mas uma amostra pequena pode não enxergar valores raros — outra origem de estimativa errada.


    
Passo 2 — ler o histograma

    
O histograma mostra o que o otimizador “sabe” sobre cada faixa de valores. Para a estatística do índice de ProductID:

    

      

        T-SQL
        
      

      

        

        
SELECT
  h.step_number,
  h.range_high_key     AS valor_de_corte,
  h.equal_rows         AS linhas_no_valor,
  h.range_rows         AS linhas_entre_cortes,
  h.average_range_rows AS media_por_valor_entre_cortes
FROM sys.stats AS s
CROSS APPLY sys.dm_db_stats_histogram(s.object_id, s.stats_id) AS h
WHERE s.object_id = OBJECT_ID(N'Sales.SalesOrderDetail')
  AND s.name = N'IX_SalesOrderDetail_ProductID'
ORDER BY h.step_number;

      

    

    
Se a consulta filtra ProductID = 870 e 870 é um valor de corte, a estimativa sai de linhas_no_valor. Se o valor cai entre dois cortes, sai de media_por_valor_entre_cortes. O DBCC SHOW_STATISTICS mostra o mesmo conteúdo, em formato mais antigo.


    
Passo 3 — montar o cenário

    
Para ver o efeito sem esperar o problema acontecer, a demonstração cria uma cópia dos itens de pedido com um produto que existe em uma linha só. O índice é criado nesse momento — e a estatística dele registra que o produto 9999 é raro.

    

      

        T-SQL
        
      

      

        

        
SELECT SalesOrderID, SalesOrderDetailID, ProductID, OrderQty, UnitPrice
INTO dbo.DemoItemPedido
FROM Sales.SalesOrderDetail;

-- O produto 9999 começa com uma única linha
INSERT INTO dbo.DemoItemPedido (SalesOrderID, SalesOrderDetailID, ProductID, OrderQty, UnitPrice)
VALUES (43659, 9000000, 9999, 1, 10.00);

CREATE CLUSTERED INDEX CX_DemoItemPedido
  ON dbo.DemoItemPedido (SalesOrderID, SalesOrderDetailID);

-- NORECOMPUTE impede a atualização automática desta estatística
CREATE INDEX IX_DemoItemPedido_ProductID
  ON dbo.DemoItemPedido (ProductID)
  WITH (STATISTICS_NORECOMPUTE = ON);

-- Uma carga grande: o produto 9999 passa a ter 100 mil linhas a mais
INSERT INTO dbo.DemoItemPedido (SalesOrderID, SalesOrderDetailID, ProductID, OrderQty, UnitPrice)
SELECT TOP (100000) SalesOrderID, SalesOrderDetailID + 1000000, 9999, OrderQty, UnitPrice
FROM Sales.SalesOrderDetail;

      

    

    
O STATISTICS_NORECOMPUTE = ON existe só para a demonstração: ele desliga a atualização automática daquela estatística e garante que a fotografia antiga continue lá. Na vida real o efeito aparece sem essa opção — quando a carga não chega ao limite que dispara a atualização, ou quando a atualização acontece por amostragem e não enxerga a mudança.


    
Passo 4 — ver a estimativa errar

    
No SSMS, ligue o plano de execução real (Ctrl + M) e rode a consulta com as medições de leitura e tempo:

    

      

        T-SQL
        
      

      

        

        
SET STATISTICS IO, TIME ON;

SELECT SalesOrderID, ProductID, OrderQty, UnitPrice
FROM dbo.DemoItemPedido
WHERE ProductID = 9999;

      

    

    
Passe o mouse sobre o operador de leitura do índice e compare dois números:

    
    
      
  • Número estimado de linhas (Estimated Number of Rows): poucas linhas, porque a estatística ainda diz que o produto 9999 é raro.
    • 
      
  • Número real de linhas (Actual Number of Rows): 100.001.
    • 
    

    
Confiando na estimativa, o otimizador escolhe buscar no índice de ProductID (Index Seek) e, para cada linha encontrada, ir à tabela buscar OrderQty e UnitPrice (Key Lookup). Para poucas linhas é o caminho certo. Para 100 mil, são 100 mil idas à tabela — e a aba Mensagens mostra isso em logical reads muito acima do tamanho da própria tabela.


    
Passo 5 — atualizar e comparar

    
Atualize a estatística lendo a tabela inteira e rode a mesma consulta de novo:

    

      

        T-SQL
        
      

      

        

        
UPDATE STATISTICS dbo.DemoItemPedido IX_DemoItemPedido_ProductID
  WITH FULLSCAN;

SELECT SalesOrderID, ProductID, OrderQty, UnitPrice
FROM dbo.DemoItemPedido
WHERE ProductID = 9999;

      

    

    
Agora a estimativa fica perto das 100 mil linhas, e o plano muda: o otimizador lê a tabela inteira de uma vez (Clustered Index Scan), em vez de fazer 100 mil buscas. As logical reads caem para algo próximo do número de páginas da tabela. Nada no código mudou — só a informação que o banco tinha sobre os dados.

    
A estatística atualizada invalida o plano guardado em cache, e a próxima execução é compilada de novo com os números novos. Por isso não é preciso limpar o cache para ver a diferença.


    
Quando o banco atualiza sozinho

    
Com AUTO_UPDATE_STATISTICS ligado (o padrão), o SQL Server atualiza uma estatística quando ela vai ser usada e o contador de modificações passou do limite. Desde o nível de compatibilidade 130 (SQL Server 2016), o limite é o menor entre 500 + 20% das linhas e a raiz quadrada de 1.000 × linhas. Numa tabela de 10 milhões de linhas, isso dá 100 mil modificações.

    

      

        T-SQL
        
      

      

        

        
SELECT
  name,
  compatibility_level,
  is_auto_create_stats_on,
  is_auto_update_stats_on,
  is_auto_update_stats_async_on
FROM sys.databases
WHERE name = N'AdventureWorks2025';

      

    

    
A atualização automática ajuda, mas não cobre tudo: ela usa amostragem, só acontece quando a estatística é usada, e uma carga logo antes de um relatório pode cair abaixo do limite. Colunas de data ou de código sequencial sofrem mais — os valores novos ficam sempre além do último corte do histograma.


    
Uma rotina para não depender da sorte

    
A consulta abaixo lista, no banco inteiro, as estatísticas com mais modificações em proporção ao tamanho da tabela. É um bom ponto de partida para decidir o que atualizar fora do horário de uso:

    

      

        T-SQL
        
      

      

        

        
SELECT
  OBJECT_SCHEMA_NAME(s.object_id) AS esquema,
  OBJECT_NAME(s.object_id)        AS tabela,
  s.name                          AS estatistica,
  sp.last_updated                 AS atualizada_em,
  sp.rows                         AS linhas,
  sp.modification_counter         AS modificacoes,
  CAST(100.0 * sp.modification_counter / NULLIF(sp.rows, 0) AS DECIMAL(12, 1)) AS pct_modificado
FROM sys.stats AS s
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS sp
WHERE OBJECTPROPERTY(s.object_id, 'IsUserTable') = 1
  AND sp.modification_counter > 0
ORDER BY pct_modificado DESC;

      

    

    
Alguns cuidados na hora de atualizar:

    
    
      
  • UPDATE STATISTICS ... WITH FULLSCAN lê a tabela inteira: estimativa melhor, custo maior. Em tabelas muito grandes, WITH SAMPLE 25 PERCENT é um meio-termo.
    • 
      
  • sp_updatestats atualiza tudo que teve alguma modificação, com amostragem padrão — e pode trocar por uma amostra pequena uma estatística que tinha sido montada com FULLSCAN.
    • 
      
  • Reconstruir um índice (ALTER INDEX ... REBUILD) atualiza a estatística daquele índice lendo a tabela inteira. Reorganizar (REORGANIZE) não atualiza nada.
    • 
      
  • Depois de uma carga grande, atualizar as estatísticas das tabelas carregadas faz parte da carga — não precisa esperar o relatório ficar lento.
    • 
    


    
Limpar o ambiente

    

      

        T-SQL
        
      

      

        

        
SET STATISTICS IO, TIME OFF;
DROP TABLE IF EXISTS dbo.DemoItemPedido;

      

    


    
Para levar

    
    
      
  • Consulta que ficou lenta sem mudança de código: compare linhas estimadas e reais no plano antes de criar índice ou reescrever a consulta.
    • 
      
  • Diferença grande entre as duas é sinal de estatística desatualizada ou montada com amostra pequena.
    • 
      
  • sys.dm_db_stats_properties mostra quando cada estatística foi atualizada e quanto a tabela mudou desde então.
    • 
      
  • Depois de cargas grandes, atualize as estatísticas das tabelas carregadas como parte do processo.
